# Osmo Pocket Video Slimming

`slim_videos.py` は DJI Osmo Pocket 4P の動画から、Google Photos 用の軽量な MP4 を作ります。元動画は変更しません。

## 全編2K一括変換・実出力の評価（2026-11-07）

**元動画6本すべてから、2560×1440 / 29.97fps / HEVC Main 10 / 10bit の `*_slim.mp4` を作成済みです。** 以前のフルHD出力も元の4K動画から作り直しました。元動画は変更していません。

合計 **21.79GB → 7.29GB（66.6%削減）** になりました。サイズは10進表記です。

### 劣化の評価

4Kから2Kへの縮小により画素数は約44%になり、細かな文字・布地・葉の質感は拡大すると減っています。残り5本では、確認した比較画像に目立つ色の変化や大きなブロックノイズは見られず、上記の画質指標も良好でした。画質が全く変わらないという結果ではありません。

**`0006` は例外です。** 42Mbpsまで上げても、冒頭約0.6〜5.6秒の草木・細いフェンスなどに圧縮の差が残りました。全編平均0.9789だけを見ると良さそうですが、この5秒間は0.9442で、1フレームの最低値は0.9157でした。比較フレームの時刻ずれが原因でないことも、前後1フレームをずらした比較で確認しました。この動画だけは削減も約152MBと小さいため、元の4K動画を使う方が今回の画質優先の方針に合います。依頼どおり2K版も残してあります。ほか5本の2K出力と `0006` の元動画を使う場合、合計は約7.44GBです。

`0005` は12Mbps出力の全編検査で、事前の3区間検査に含まれない約5.4秒からの5秒間にSSIM 0.9693を検出しました。18Mbpsで作り直し、この値を0.9778に改善しました。`0006` の42Mbps指定では短区間の推定削減率が19.6%だったため、候補作成時だけ `--min-savings 0` を指定しました。画質検査は有効なままで、全編出力の実際の削減率は21.7%でした。

### 検証した範囲

- 6本すべて、出力の映像・音声を全編デコードし、エラーがないことを確認。
- 全151,118フレームの数、動画の長さ、10bit、Rec.709、撮影日時を確認。AAC音声のパケット内容は元動画と完全一致。
- `0002` / `0005` / `0006` / `0007` は全フレーム、長尺の `0001` / `0004` は冒頭から終端まで等間隔の13区間×8秒を元動画と比較。合計17,121フレームを画質測定。
- SSIMとPSNRは、**元の4K動画を同じ2560×1440にLanczosで縮小したもの**を基準に測定。4Kから縮小すること自体の情報損失は、このSSIMには含まない。
- 測定した区間の中で5秒間の移動平均も計算し、全編平均だけでは埋もれる短い劣化を検出。
- 各動画でSSIMが最も低かったフレームを画像化し、通常の全景比較と、4K原画に対する拡大比較を目視確認。

長尺2本は画質を全フレーム測定したわけではありません。SSIMは見た目の完全な保証ではなく、今回の採用判断の補助です。

## 初回のサンプル評価

以下は一括変換に先立つ、解像度とビットレートを選ぶための調査記録です。現在の全編2K出力の結果は上記を参照してください。

2026-11-07 に、6本・合計21.79GBを調査しました。6本とも **3840×2160 / 29.97fps / HEVC Main 10 / 10bit / Rec.709** でした。

- **撮影日時の追加は不要でした。** コンテナと映像・音声トラックに `creation_time` があり、ファイル名の時刻とも0〜1秒の差で一致します。例えば `DJI_20261107124028_0007_D.MP4` の既存値は `2026-11-07T03:40:29Z`（日本時間12:40:29）です。この1秒差も既存値を優先します。
- **アップロード用の圧縮には効果があります。** 映像は約28〜50Mbps。1080p / 8Mbps の短区間比較では約76〜84%の削減が見込めました。ただし細部や動きが多い動画では画質指標が下がるため、全動画を同じ低ビットレートで処理しません。
- `0001` は11.19GBで、[Google Photos の動画10GB上限](https://support.google.com/photos/answer/6193313?hl=ja)を超えています。
- Google Photos が常に4Kを失うわけではありません。[「元の画質」は解像度を保持し、「保存容量の節約画質」は1080p超の動画を1080pに縮小します](https://support.google.com/photos/answer/6220791?hl=ja)。現在の既定は **2K（2560×1440）** です。`--2k` で明示的に選べます。フルHD（1920×1080）にしたい場合は `--full-hd` を指定してください。

### 実測した比較

各動画の中央10秒を、同じ M3 MacBook Air / FFmpeg 8.1 のハードウェア HEVC で変換しました。SSIM は**同じ解像度に縮小した元動画との比較**です。4Kから縮小すること自体の情報損失は、この数値には含みません。

| --- | ---: | ---: | ---: |
| 0001 | 0.9883 | 0.9907 | 0.9921 |
| 0002 | 0.9887 | 0.9909 | 0.9924 |
| 0004 | 0.9957 | 0.9959 | 0.9961 |
| 0005 | 0.9643 | 0.9718 | 0.9750 |
| 0006 | 0.9151 | 0.9332 | 0.9458 |
| 0007 | 0.9790 | 0.9830 | 0.9844 |

1080p / 8M の変換速度は再生時間の約3.1〜4.8倍、1440p / 12M は約3.1〜3.3倍でした。起動・短区間の読み込み・音声コピー・MP4書き出しを含み、画質測定時間は含みません。全編で同じ速度になるとは限りません。

さらに **フルHD設定（`--full-hd`）** で各動画の前半・中央・後半から5秒ずつを検査した結果、次の判断になりました。以下は2Kの判定結果ではありません。

| 動画末尾 | 判断 | 採用ビットレート | 3区間中の最低SSIM | 容量削減見込み |
| --- | --- | ---: | ---: | ---: |
| 0001 | 圧縮 | 8M | 0.9910 | 約76% |
| 0002 | 圧縮 | 8M | 0.9900 | 約77% |
| 0004 | 圧縮 | 8M | 0.9919 | 約77% |

| 0006 | 元動画を使用 | 27Mまで試しても不合格 | 0.9636 | 圧縮しない |
| 0007 | 圧縮 | 8M | 0.9819 | 約80% |

当初、`0007` をフルHD設定で全編変換して検証しました。**284,658,872 bytes → 55,852,684 bytes（80.4%削減）**、1920×1080 / HEVC Main 10 / 29.97fps / 1605フレームでした。撮影日時とRec.709を保持し、AAC音声2510パケットの内容も元動画と完全一致しました。このフルHD出力は、その後、上記の全編2K出力に置き換えています。

SSIM は画質の目安です。3区間の検査は動画全体の見た目を保証しません。比較用の動画は `evaluation/` にあるので、必要なら再生して確認できます。Google Photosへの実アップロード・撮影日の表示確認は行っていません。

## 使い方

必要なものは Python 3.9以降、`ffmpeg`、`ffprobe` です。既定の圧縮には macOS の `hevc_videotoolbox` を使います。Apple Silicon では主に専用メディアエンジンで処理し、ソフトウェアエンコードへの自動切り替えはしません。

```bash
cd /Users/yusuke-iwaki/Desktop/osmoslim

# メタデータ・映像形式を調べるだけ（書き込みなし）
python3 slim_videos.py --analyze

# 短区間だけを試し、画質・圧縮効果を判定する（全編出力なし）
python3 slim_videos.py --sample-only

# このフォルダを2Kで一括処理（既定）。*_slim.mp4 を作る
python3 slim_videos.py

# フルHDで一括処理。出力は別名にする
python3 slim_videos.py --full-hd --suffix _full_hd_slim.mp4

# 1本だけ処理
python3 slim_videos.py DJI_20261107113403_0005_D.MP4

# 2Kを明示指定（縦動画は1440×2560）。出力は別名にする
python3 slim_videos.py --2k --suffix _qhd_slim.mp4

# 日時がない動画だけ、映像・音声を再圧縮せずに日時を補う
python3 slim_videos.py --metadata-only

# 実行予定のコマンドを見る。実行時はさらに画質検査・出力検証をする
python3 slim_videos.py --dry-run
```

既存の出力はスキップします。以前作成したフルHDの出力を2Kに作り直す場合は、`--overwrite` または別の `--suffix` を指定してください。変換失敗時や中断時に既存の完成ファイルを壊さないよう、一時ファイルを検証してから置き換えます。スキップした動画の代わりのファイルは作らないため、その動画は元ファイルをアップロードしてください。

`--full-hd` と `--2k` は同時に指定できません。任意の長辺を指定する従来の `--max-dimension` も残していますが、これらの解像度オプションとの併用はできません。

## 圧縮方針

- 既定は2K（長辺2560）。`--full-hd` は長辺1920です。縦横比を保ち、拡大しません。フレームレートを意図的に落としません。
- 既定は HEVC。10bit素材は10bit、Rec.709などの色情報も保持します。従来の H.264 / 8bit への変換は明示指定時だけです。
- 自動ビットレートは出力画素数とfpsに応じて決定します。1080p30は8Mbps、1440p30は12Mbpsから開始します。縦向きという理由だけでビットレートを増やしません。
- 10%・50%・90%付近から各5秒を抽出し、最低SSIM 0.97・削減率20%以上を要求します。短い動画は中央1区間です。
- 自動ハードウェア設定で画質が足りない場合、ビットレートを最大3回、約1.5倍ずつ上げて再試行します。2K/30fpsなら12→18→27→40Mbps、フルHD/30fpsなら8→12→18→27Mbps。それでも不合格なら圧縮しません。ビットレートを手動指定した場合は上げません。
- 全編出力後も実際のサイズを確認し、20%未満の削減なら圧縮出力を採用しません。日時の補完だけ必要なら、再圧縮せずに補います。
- AAC音声はコピーします。MP4にコピーできない音声形式はAAC 192kbpsへ変換します。
- DJI固有の `djmd` / `dbgi` データ、タイムコードトラック、埋め込みJPEGは出力に含めません。映像・音声と、FFmpegが扱えるコンテナメタデータを保持します。DJIの編集用データも必要な場合は元動画を保管してください。
- メーカー・機種は既存タグまたは `encoder=DJI OsmoPocket4P` から取得します。ファイル名だけから機種名を作りません。
- HDR / D-Log / Dolby Visionは、このSDR向け処理では圧縮を見送ります。日時補完のためのストリームコピーは可能です。

しきい値や速度を明示的に変更できます。

```bash
# 固定ビットレート。画質検査は有効なまま
python3 slim_videos.py --video-bitrate 12M --video-maxrate 24M

# 画質をより厳しく検査する
python3 slim_videos.py --min-ssim 0.98 --sample-seconds 10

# 速度優先。画質検査は有効なまま
python3 slim_videos.py --hw-speed

# CPUエンコードを明示的に使う場合（HEVC 10bitを維持可能）
python3 slim_videos.py --video-encoder libx265 --crf 20
```

`--force` は画質・削減率の検査を省略します。通常は不要です。`--video-encoder h264_videotoolbox` / `libx264` も選べますが、10bit SDR素材は8bitになります。

## 日時の方針

既存の有効な撮影日時を優先し、元の値をファイル名の時刻で置き換えません。優先順位はコンテナの `creation_time` / QuickTime撮影日時、主映像、その他の映像・音声ストリームです。

有効な日時がどこにもないときだけ、次のファイル名から推測します。1904年・1970年などの未設定値は使用しません。ファイルの更新日時から撮影日時は作りません。

- DJI: `DJI_20261107124028_0007_D.MP4`
- Insta360型の日時表記: `VID_20261107_124028_012.mp4`

推測時のタイムゾーンは `Asia/Tokyo` で、UTCに変換して記録します。旅行先の時刻で撮影していた場合は `--timezone Europe/Paris` などを指定してください。既存の撮影日時にはこのオプションは影響しません。

ファイル名からの上書きが本当に必要な場合だけ、`--date-from-filename` を指定します。日時不明かつファイル名にも時刻がない動画は、日時を捏造せずログに不明と表示します。
